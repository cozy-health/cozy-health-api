# Store-confirmed plan status, without Cozy invoices

Store lookups and writes are serialized per account through a shared primary-database lock. Versioned state transitions distinguish a real cancel-and-reactivate cycle from a duplicate callback, and delivery requires both the latest version and matching snapshot. No user-row transaction is held open while external store HTTP calls run.

Development only. The user chose store-issued receipts instead of a second Cozy invoice or VAT calculation. Store billing remains disabled until developer accounts, products, credentials and sandbox tests are ready. `STORE_PLAN_EMAILS_ENABLED` also defaults to false; both it and `STORE_BILLING_ENABLED` must be true to record or send automatic plan emails. Tests enable these flags only in isolated fixtures.

Verified store responses now preserve a safe plan snapshot: platform, state, automatic-renewal status when known, trial status when known, environment and confirmed end date. No price, VAT, proceeds, raw purchase token or clinical content enters the notification snapshot. Apple renewal information is signature-checked and bound to the same original subscription; verified grace-period expiry can preserve temporary access. Google active, canceled, grace, hold, pending, paused and expired states remain distinct. Google voided-purchase notifications trigger a fresh store lookup rather than directly changing access.

The subscription response includes official management/purchase-history links only for an owned verified store record. It preserves payment holds and revocations instead of presenting them as an ordinary active plan. An expired date cannot be labelled a future renewal. Annual subscriptions remain eligible for server reconciliation even if their previous check is older than sixty days.

Unique notification snapshots suppress repeated verification/restore callbacks and stale queued updates. The database outbox and encrypted database-queue insertion commit together. Notifications wait for required store acknowledgement. Queue insertion failure does not undo confirmed access, and pending work is recovered by `stores:dispatch-plan-emails`. Delivery checks current account activity, verified email identity and current store state; expired active notices are suppressed. Mail transport retries are bounded; operator retries remain possible. SMTP acceptance is not proof of inbox receipt, and ambiguous transport timeouts cannot promise exactly-once delivery.

The app shows plan state, the confirmed renewal/end date, and actions to manage the subscription, view the store's purchase history and refresh status. It follows the store that owns the purchase, not the current phone platform. Only approved store URLs can be launched; launch failures use a centred recovery dialog. Hive fields are appended without reusing the previous field numbers, and development grants cannot become store purchases. Management views retain account-owner checks and scrolling for large text.

Validation includes cryptographically signed isolated Apple response fixtures, Google HTTP response fixtures, duplicate calls, extensions, grace/cancellation, hold, wrong-account binding, queue failure, acknowledgement recovery, account/email changes, stale notices, operator retry, payload encryption and annual reconciliation. Mobile tests cover store selection, link rejection, cached-account separation, small phones, large text, light/dark themes and recovery dialogs. Real App Store/Google Play sandbox purchases, signed device acceptance and activation still require the developer accounts and separate activation approval.

Primary references: [Apple subscription management](https://support.apple.com/en-us/118428), [Google order history](https://support.google.com/googleplay/answer/2850369), [Google subscription state reference](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2). No payment receipt or tax invoice is generated by this feature.
