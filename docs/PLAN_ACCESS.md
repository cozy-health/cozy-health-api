# Plan permissions (development rollout)

`PLAN_ACCESS_ENABLED` defaults to false for staged rollout. Enable only on the explicitly approved Railway development API and worker after migration, mobile validation and development deployment checks. `/api/v1/config` exposes the effective `flags.plan_access` from environment configuration; a database flag cannot override it. Disabling the flag restores the previous behavior without deleting records. This is independent of the development test grant flag and the store billing flag.

`GET /api/v1/me/plan-access` returns private/no-store account-specific permissions, the active tier, expiry and development-test source. Active Standard permits written journals, moods and community reading. Student/Premium permit those plus voice, provider connection/chat, new journal sharing, assessments, challenges and community participation. No active subscription (including expired, future-start, inactive or legacy Free) grants no new plan actions. Emergency and existing private records remain accessible. Breathing/grounding, support, account recovery and existing export functions retain their existing availability; no new clinical or assistant feature is introduced.

The middleware checks consumer REST writes. SyncRecordWriter applies the same journal/mood/assessment permissions to batch upserts. A denied sync operation returns `error_code=plan_required`; other operations continue, and the app retains the local record/queued change for retry. Client-supplied subscription sync writes remain forbidden. A nominally written journal containing voice metadata also requires voice access. Provider accounts retain their existing independent privacy/consent controls, without a billing requirement.

Reading/downloading owned old journals, voice attachments, messages and assessment results remains under existing ownership checks without plan gating. Revoking sharing, deleting one's data, leaving groups, reporting/blocking and viewing the blocked list remain possible after expiry. Enabling new provider consent requires Premium/Student, while withdrawing it does not. Active existing provider consent is not silently revoked by a plan change.

The app checks permissions before restricted offline saves and key actions, uses centered explanations and gates the assessment-taking/post-creation routes. Offline permission reuse is per account, limited to a finite last-verified plan expiry, and only used for network/timeout failures. The server always rechecks writes, so a cached client permission cannot bypass a revoked/expired grant. Full permission enforcement requires the server flag; old clients still encounter server denials. Plan denial is not an expired login and must not clear credentials. Session/account changes abort permission reuse and local writes.

The catalog migration archives Free offerings and adds Nigerian Standard at 6,500 NGN, preserving Student 5,000 and Premium 10,000. These are catalog references with the existing annual discount; purchased subscriptions, receipts and renewal amounts are untouched. No provider or institution billing is added. Store billing remains held and cannot be activated by a test grant. Standard is accepted as a future product tier but no store product or developer account is created.

Development grants overlay a real plan only while valid in the exact development environment. Revoking a grant reveals the genuine plan immediately on subsequent server requests. New plan permissions do not perform student approval/renewal, institution redemption or store purchase verification; those remain separate services and outstanding approved work.
