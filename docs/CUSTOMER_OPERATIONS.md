# Customer support and privacy requests

Development implementation, 3 November 2026. Additive migration `2026_11_03_000001_add_support_threads_and_privacy_requests.php`. Existing clients can continue submitting subject/message to POST `/api/v1/support/reports`; new clients also send a UUID `request_id` for idempotency.

## Support contract

- Customer GET `/support/reports?page=1` returns `data` containing Laravel pagination (`data`, `last_page`, etc.). GET `/support/reports/{id}` returns `data` with id, subject, original message, status, integer version and ordered messages (id, author customer/support, body, created_at). Staff notes, delivery identifiers and staff identity are absent.
- POST `/support/reports/{id}/replies`: body (1-10000 characters), request_id UUID, expected_version integer >=0. Identical retries return the existing message even after the version changes; altered reuse or a stale new reply returns 409. Customer replies reopen resolved requests.
- Admin GET `/support/{id}/thread` adds staff-only admin_notes, record_version and notification_status. POST `/support/{id}/replies` uses the same reply payload. POST `/support/{id}/messages/{uuid}/retry` retries only failed/bounced/suppressed notification attempts, not the message. Existing PUT `/support/{id}` handles private notes and explicit resolve/reopen with the record_version optimistic token.
- New messages are encrypted and have a server sequence. Message, inbox notification and database email job commit together. Generic email has no support/health text; `/support-inbox` is a public, generic app-opening page. Queued mail rechecks current recipient, active/verified account and latest delivery attempt. Queued/sent are not proof of inbox receipt.
- All admin support routes require `admin:support` and current ID assignment in `SUPPORT_REVIEWER_IDS`; moderation no longer confers support access. Existing notes/history are preserved. Email retry permissions do not grant privacy rights.

## Privacy contract

- Customer GET `/privacy-requests?page=1` returns owner-only pagination. POST requires kind export/correction/deletion, request_id UUID, current password, confirmed=true and optional changes. Verified email is required. Passwords are verified using the existing password hash and never persisted. A credential fingerprint invalidates requests after identity changes.
- Corrections allow existing editable profile fields only (name, username, bio, timezone, country_code), use existing profile validation/update behavior, and do not alter clinical history or account identity. Changes/outcome are encrypted. The outcome is customer-visible; internal staff notes belong in support, never this field.
- Admin GET `/privacy-requests` supports page/status; GET `/{id}` reads a request; POST `/{id}/process` requires decision approve/hold/decline, expected_version >=1 and customer-visible outcome (1-1000 characters). Existing decisions cannot be silently overwritten. Only assigned `PRIVACY_REVIEWER_IDS` with `admin:privacy` may process; support/moderation/users roles alone are denied. Both assignment and capability are enforced server-side.
- Approval makes an export downloadable by its customer, applies the requested validated profile correction, or durably queues deletion. Deletion runs through the existing account/file cleanup service, with Apple revocation outside database transactions. Encrypted database jobs use the `default` queue, recheck approval version/current reviewer/identity, retry three times with existing mail-style backoff and expose exhausted failures for reviewed retry. Account rows disappear on successful deletion; private-file cleanup still uses `avatar_photo_deletions`. Do not call pending physical cleanup complete.
- POST customer `/privacy-requests/{id}/download` requires current password and completed export approval. Returns an authenticated ZIP, no public link or email payload. It includes retained customer-owned cloud domains and owned audio/avatar/community-image/retained Student-evidence files. Manifest lists inclusion/exclusion boundaries. Provider-internal notes/reports, other accounts, credentials, receipts/tokens and staff notes are excluded. Missing retained files fail preparation with 503; no partial-success export is returned. Temporary private files are cleaned after streaming/shutdown; no persistent export copy or new retention period is introduced. Existing device JSON remains separately labeled.
- Submission and download have separate five/hour and three/hour account rate buckets. Support/privacy remain accessible through consent recovery, while existing session protection and ownership still apply. No enrollment/consent/store flag is enabled.

## Operational rollout / evidence

Reviewer lists default empty; owner must name actual staff before development activation. No credentials, actual assignments, policy readiness or retention approvals are fabricated. Workers must service the existing database `email` and `default` queues and existing private-file cleanup scheduler. Local tests use SQLite/fakes; MySQL/concurrency CI and real app/browser/inbox/device acceptance are tracked separately in the workspace execution register. This feature is not production activated.
